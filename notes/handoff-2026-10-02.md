## Findings worth keeping

**The model-budget habit is real but not fixable by removing counters.** The
first Sonnet invented a tool-call budget out of nothing ("plan conservatively
for maybe 80–150 calls"). r21.1/r21.2 (which removed counters, compute time,
limits) still produced "aim for roughly 60–120 chunks, efficient but thorough",
"Given my effort budget", "keep an eye on compute time". With nothing left to
count it invents a new unit (chunks, "effort"). The user's own prompt line
"You are not being evaluated in a quantifiable way" (r21.2) is the closest
thing to a counter and it didn't fully stop it either. Conclusion: mostly a
training habit — don't over-engineer against it.

**trees.md steers the subject, but only the odd phrasing.** Every Sonnet
planned a dusk scene around a stag-headed oak; the phrase was trees.md's.
Removing that lead (r21.5) changed the *staging* (it did NOT go portrait, went
back to 1.4 landscape) but it still painted a big bare oak — trees.md's
construction knowledge still pulls "tree" to the center. A single motif note
for one artist is a real steering force; a general "how to build organic
branching" note would be fairer.

**The r21.5 painting reads worse than r19 — and the logs say why.** Not effort
(more chunks, more time, a better oak). Two composition facts:
- r19 filled the big luminous field with **still water** (reflective, self-
  detailing, the ruin gets a reflection). r21.5 filled it with a **fog sea**
  ("nearly empty, as it should be") — an opaque void, so the one hard shape in
  it (the mesa / the "castle") carries all the weight and reads unfinished.
  Water self-resolves; fog doesn't.
- Symbol scale: r19's ruin = tiny distant accent (never needs detail); r21.5's
  mesa = large and prominent, so its softness is glaring. r21.5's own journal
  calls it "soft… pasted-on… the remaining weaknesses are the ones I already
  accepted" and stops. r19 verified "all hold at every scale."
- The varnish+crackle is NOT the cause; the plain canvas has the same
  weakness. Crackle just emphasizes it.
- **Do not nudge the painter about this.** The user was explicit.

## Counter / harness changes (r21.3–r21.4, in the TypeScript harness only)

No easel recompile. `paint` replies `ok` (not `ok · chunk N`); Lua errors read
`[string "chunk"]`; `status`/`log` carry no counts; each `look` gets a random
UUID filename and no seconds; the compaction/sitting summary drops chunk counts
and the globals' chunk numbers; the guide/tool table updated to match. Verified
against a real easel and by tests. Searched: no "cost"/budget/MB/pixel-limits
left in what the painter sees.

**The reply-capture bug.** `pi --print` prints the painter's reply to stdout,
but on the **Anthropic/pi-black path stdout came back empty** (exit 0, no
stderr) while the session kept the text. Fixed in every runner: the reply is
read from the **session file** (`session_reply()` — last assistant message
that is text with no pending tool call), stdout is the fallback. r21.5's live
sittings 2/3 still hit the bug (old code); their replies were recovered by
hand. pi-black itself is innocent (only makes a `gh gist`).

## Conventions to respect

- Rounds are prompt-only tags `round-<N>.<k>`; each needs a `claude-paint-r<N>.<k>`
  detached checkout and a `notes/round<N>.<k>/runner` copy. Prompt/runner changes
  don't recompile the easel (build is keyed by the code trees).
- `git commit` sweeps the whole index — check `git branch --show-current` before
  committing; a feature branch (`feat/r21-pause-between`, holding the user's
  `pause=True` chain-pause feature) is parked, not merged.
